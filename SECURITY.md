# Cartiva security posture

Last reviewed: August 25, 2026

Cartiva currently has three deliberately separate surfaces:

- The separate Site deployment has marketing pages and a fixed, explicitly labeled homepage demo. The mobile application does not depend on that deployment copy. It has no database, accounts, passwords, Cartiva sessions, uploads, customer OAuth, cart mutations, ordering, or payment handling.
- The Expo mobile client uses an anonymous read boundary for official Kroger location and product comparison. Browser origins are deny-by-default; native requests are strictly shaped and rate-limited. Optional Kroger customer authorization and cart mutation use a separate bearer-authenticated boundary, owner-scoped encrypted retailer tokens, immutable server comparison receipts, atomically one-use OAuth state, an owner-bearer-redeemed pending authorization completion, and idempotent cart operations. The browser callback never activates a customer token by itself. There is no Cartiva account, order, or payment endpoint. Cart writing remains capability-disabled until its explicit deployment gates pass.
- Legacy website and Chrome-extension customer OAuth/mutation routes remain loopback-only. The separate mobile routes are designed for a public HTTPS callback, but may be published with cart writing enabled only under the remote-backend gates below.

## Implemented controls

1. **API keys stay server-only.** Credential-reading modules have a browser-import backstop. `.env*` and `.cartiva/` are ignored, output tracing excludes them, and API responses never return provider credentials or Kroger tokens. Never use `NEXT_PUBLIC_` for a retailer credential.
2. **Git secret audit is clean.** At this review, the root repository had no commits or remote. Every reachable Sites commit, loose root object, current source, build output, and extension build was scanned without finding a credential. No destructive history rewrite is warranted. Enable hosted secret scanning when the root repository receives its first remote.
3. **No public database key exists.** Cartiva has no browser database client and Sites has no D1 or R2 binding. Do not add a secret/service-role key to browser code. If Supabase is introduced, the browser may receive only its publishable key; if D1 is introduced, it must remain server-only.
4. **Shared-database row security is a scaling gate.** No database exists today. The reviewed single-instance mode uses server-only files on one private persistent volume. Any multi-instance shared database must default-deny exposed tables and enforce owner checks in both read and write policies or equivalent server-only queries.
5. **Sensitive OAuth tokens are encrypted.** Kroger customer sessions are stored as AES-256-GCM envelopes with a fresh nonce and authentication tag. The file key is derived from server-only Kroger application credentials and is never written to disk. Legacy plaintext migration is limited to the single-user local session; mobile sessions require owner-bound version 3 envelopes and fail closed on copied or plaintext files. Changing the Kroger application secret intentionally invalidates the local session and requires reconnecting.
6. **Authorization is server-enforced at each current boundary.** Retailer credentials and OAuth exchanges remain server-side; browser requests cannot inject trusted price, provenance, location, completeness, UPCs, or quantities. The hosted Site is owner-only and exposes read-only public-catalog lookup only. Mobile cart mutation requires its signed temporary owner capability and the server-held comparison receipt; shopper signup is not required for this MVP.
7. **Mobile records are owner-scoped and fail closed.** A high-entropy, signed temporary access bearer derives a non-secret server owner key, lives for one hour, and cannot renew itself. A distinct high-entropy `r1` recovery credential preserves that owner; only its domain-separated hash is stored. Recovery expires after 30 days without a successful rotation, so abandoned installs cannot fill the durable store forever. Renewal atomically rotates current to a client-proposed next hash under the owner lock, retaining one previous hash solely for an exact lost-response retry where the proposal proves the already-current token. Authentic previous-token reuse with a different successor proves a split credential family and revokes the entire family; an unrelated invalid hash cannot revoke it. Explicit session deletion is idempotent only after the record is gone, persists revocation before returning success, and any issued access bearer ages out within one hour. Signing-key rotation may temporarily retain exactly one previous secret for access/OAuth verification; every new access token and OAuth record uses the current key. Comparison receipts, active and pending encrypted Kroger sessions, OAuth state/completions, and cart-operation records are partitioned by that owner, and cross-owner tests cover reads, forwarded callback handles, token-file swaps, disconnect cleanup, recovery rotation, key rotation, and cart replay. Kroger's callback exchanges into a five-minute pending encrypted session whose exact ciphertext digest and originating authorization epoch are sealed into its one-use completion record; only the initiating owner bearer can promote it, and a pre-disconnect completion cannot survive a deletion crash and activate later. A bounded one-minute janitor physically removes expired staged refresh tokens while the reviewed persistent process runs. Active Kroger sessions retain a separate seven-day inactivity window rather than inheriting the one-hour access lifetime. Production also requires a claimed HTTPS iOS universal link, because a custom URL scheme can be intercepted by another installed app. In the supported one-process file mode, one owner lock serializes session recovery, OAuth registration/finalization, disconnect, and cart mutation. Critical writes flush file contents, atomically rename, and sync parent-directory metadata; Windows is excluded from production file-backed cart writes because Node cannot provide that directory durability there. OAuth start, callback, and activation recheck unresolved owner cart history inside that lock; disconnect rotates a durable marker so even an already-claimed older callback cannot reconnect. The marker is safely pruned after the ten-minute state lifetime, preventing a dormant marker from pinning a retired previous signing key. A new authorization receives a new generation, so a confirmed or outcome-unknown comparison cannot be replayed with another Kroger account. Missing files (`ENOENT`) are the only empty-state case; unreadable, corrupt, malformed, or failed persistence state blocks mutation. Local-file idempotency is valid only for one process/replica on one persistent private volume. Multi-instance or serverless deployment requires a transactional shared store and distributed owner lock before cart writing is enabled.
8. **Field tampering fails closed.** JSON bodies are size-limited and strictly shaped; unknown fields, malformed list entries, invalid fulfillment modes, duplicate Kroger UPCs, excessive quantities, and baskets over 24 items are rejected instead of silently dropped or coerced. Hosted Kroger location, product identity, regular prices, stock, pickup evidence, completeness, and totals are server-derived.
9. **No Cartiva session cookie exists.** If accounts are introduced, use a managed server/BFF session with an `__Host-` cookie, `Secure`, `HttpOnly`, `SameSite=Lax` or stricter, rotation, short expiry, and server-side revocation. Do not store access or refresh tokens in browser storage.
10. **Cartiva stores no passwords.** Prefer managed authentication. If first-party passwords are ever required, use Argon2id with unique salts and an upgradeable PHC string; never store plaintext, reversible passwords, or fast unsalted hashes.
11. **Login abuse is bounded where login-like behavior exists.** Cartiva has no account login. Kroger OAuth starts are limited both at the route and inside the OAuth state owner; repeated attempts return `429` and pending state is bounded.
12. **Bot and quota abuse is bounded.** The owner-only Site's read-only Kroger POST endpoint rejects cross-origin browser requests and applies bounded per-IP request and upstream-work budgets with `Retry-After`. Local retailer searches, suggestions, store lookup, OAuth, status, disconnect, and cart mutation also have process-local budgets. Before public or multi-user release, replace isolate-local limits with durable edge limits and add a bot challenge only where abuse evidence justifies it.
13. **No database queries exist.** Parameterized queries become mandatory if a database is added. Never build SQL from request strings.
14. **Inputs are validated at trust boundaries.** ZIP codes, stores, locations, retailer IDs, product identifiers, quantities, modes, callback state, body encoding, content type, body size, item count, and optional preference fields are bounded before provider work.
15. **User content is escaped.** React renders shopper text as escaped text by default; the project contains no `dangerouslySetInnerHTML` path for shopper input. The one hand-built OAuth result page HTML-escapes all inserted text and also applies a restrictive CSP.
16. **File uploads do not exist.** The deployed site has no upload input, upload route, object store, or R2 binding. Before uploads are added, require an allowlist, magic-byte validation, size/count limits, randomized object names, malware scanning, private storage, and authenticated download authorization.
17. **Responses are minimized.** Hosted Kroger responses expose only shopper-visible store, source, match, regular-price, completeness, and safe handoff fields. OAuth status returns booleans only; tokens and credentials are never serialized; cart responses strip internal fingerprints and expiry data; provider failures use controlled messages rather than raw credential-bearing URLs.
18. **Security headers are active.** Both the local app and deployed site send CSP, clickjacking protection, MIME-sniffing protection, a restrictive permissions policy, referrer protection, and cross-origin isolation headers appropriate to each surface.
19. **HTTPS is forced for the deployed site.** The Sites worker redirects non-loopback HTTP to HTTPS and emits HSTS. Local development intentionally remains HTTP on loopback so HSTS cannot break the local bridge.
20. **Dependencies are scanned.** The root app has zero production or development advisories after upgrading Next.js and its locks. The deployed Sites runtime has zero production advisories. Two build-only `image-size` advisories remain in the Vinext toolchain because the advisory's stated patched version is not published; Cartiva does not accept or process ICNS, JXL, or HEIF files. The Expo lock currently reports 11 moderate entries through Expo's Node-only `xcode` → legacy `uuid` build-tool chain; Expo Doctor passes all checks, and npm's proposed fix is a breaking Expo downgrade. The native app does not execute that Xcode parser at runtime. Recheck both upstream toolchains before distribution rather than forcing incompatible overrides.
21. **The mobile boundary is capability-limited.** Only registered live retailer adapters are exposed. Kroger is `ACTIVE`; no placeholder retailer produces results. Mobile capabilities report `SHOPPING_PAGE_ONLY` unless secure session, registered HTTPS callback, explicit cart-write opt-in, and reviewed secure-state configuration are complete. Authenticated search persists exact-store product evidence; cart requests accept only the comparison ID and derive UPCs, quantities, location evidence, and completeness server-side. An incomplete basket cannot expose a winning complete total or reach cart mutation. A complete basket with merely likely availability can be reviewed, but only fresh (15 minutes or less), exact-store, `VERIFIED_IN_STOCK` lines may reach automatic cart mutation. Freshness is checked again after owner-lock and token work, immediately before recording the operation intent and calling Kroger. Mobile search also charges a bounded per-owner/client work budget for the worst-case progressive-search fan-out before provider calls begin, while the matching pipeline keeps bounded concurrency.

## Local secret handling

`.env.local` and `.cartiva/` are excluded from Git, but this workspace is inside a OneDrive-synchronized directory. Git ignore does not prevent cloud synchronization. Keep production values in the hosting provider's secret store. For local development, either move the workspace outside OneDrive or explicitly keep credential-bearing files out of synchronization, and restrict their Windows ACLs to the current user, SYSTEM, and administrators.

Do not paste credentials into issues, screenshots, test fixtures, documentation, browser storage, or extension settings. Rotate a credential immediately if it is ever exposed.

## Remote mobile-backend release gate

Before mobile customer OAuth or cart writing is enabled on a public backend, Cartiva needs all of the following in one reviewed release:

- an HTTPS API origin and exact Kroger-registered callback;
- a claimed HTTPS iOS universal return link with the production AASA/team/bundle binding (never the custom scheme);
- high-entropy signed temporary owner sessions stored only in iOS secure storage;
- server-only secrets plus encrypted, owner-bound retailer-token storage;
- either exactly one backend process on one private persistent encrypted volume, or a transactional shared store with owner enforcement;
- CSRF protection for cookie-authenticated mutations;
- durable per-account and per-IP rate limits;
- a trusted edge that strips caller-supplied forwarding headers before setting its own client-IP header (the process-local fallback limiter is not a public security boundary);
- `CARTIVA_TRUSTED_EDGE=true` only after that edge also prevents direct access to the backend origin;
- transactional, owner-scoped cart idempotency and owner-operation locking across workers;
- an explicit `CARTIVA_ENABLE_KROGER_CART_WRITES=true` release decision;
- adversarial tests proving cross-owner reads, concurrent OAuth state use, disconnects, verification reuse, stale/unverified inventory, and duplicate cart mutations all fail safely.

The legacy extension is not authorized to use this public mobile boundary. A future remote extension requires its own authenticated pairing design.
